# 真实资源库性能调查：发布构建与 Post-0.2.1

2026-10-24；开发基线 `dev/post-0.2.1 / 917a57f`。仅调查与隔离脚本，**未修改业务源码、未修复或关闭 Issue**。关联 #26、#27、#40、#46、#53、#54。原始数据、目录名、资源名称及图片不进入本报告或 GitHub。

## 结论与证据强度

1. **确认仍存在的同步热点：分类目标菜单。** 开发版右键菜单构建约 0.85 s；两次定向 profile 为 1.067/0.959 s，其中重复分类路径投影占 0.692/0.615 s。不是缩略图 loaded 门槛，也不是等待 Hover 才允许右键。
2. **确认导入通知缺少逐提交呈现。** 不排序的干净 8 张真实大 GIF 实验中，首个可靠接纳至占位绘制 6.535 s、缩略图实际绘制 6.572 s。约 5.163 s 等待剩余接纳/批次通知，1.106 s 用于结束回调；缩略图附着仅发生在其后。排序会顺带刷新投影，不能把它当成自动渐进导入。
3. **确认已有 G-14 修复有效，但不是全部响应问题的答案。** 同数据/同依赖的发布源码单资源预览元数据+信息约 879–913 ms，开发版约 40–47 ms。旧全库分类映射路径已消除，不应重写或撤销。
4. **短延迟预览会增加真实滚轮路径的工作，但未复现旧秒级卡顿。** 有效原生滚轮组指针不动、真实命中变化：100 ms 图片组心跳最大 79.7 ms，非卡片/1000 ms 组约 19.5/20.9 ms。不能据此把所有操作归为预览问题。
5. **自然内存压力确实存在，尚无完整因果归因。** 可用物理内存约 1.8–3.2 GiB 量级，系统有页面读入及较高 CPU；没有测得 Nekori GUI 的进程级硬缺页栈或 Ready/Wait 持续时间，不能把系统换入全部归给它，也不能以 Eagle 内存数值解释差异。

- 正在运行的正式安装版 PID 31720，版本 0.2.1.0；安装 `BUILD_INFO.json` 为 `6657e895526af233ae7d102070b73daf74aa7b49`。只读比较确认，该提交与 v0.2.1 标签 `77573fc` 的 fluent_ui/services/main.py/version.json 无差异。

- **实际同一安装 EXE** 在环境变量明确指向副本、热键留空的 `--smoke-test` 下验证：独立 PID 68120，退出 0，报告确认 Library 为测试副本，进程总经过约 14.0 s。该参数启动后约 1200 ms 自动退出；普通启动仍是全局单实例锁。不能安全地用它做长时间交互而又保留原进程，因此没有篡改安装包/锁来延长测试。

## 3. 已确认的 GUI 同步路径

### 3.1 右键不是在等待 Hover

`GalleryInterface.show_context_menu → _build_resource_menu`（gallery_view.py:2513/2550）先取消预览，随后分别构造加入/移动分类菜单。`CategoryTargetMenu.__init__`（category_menu.py:15）各自读取 `StorageService.node_choice_rows`（storage.py:349），后者递归调用 `Index.content` 读取节点与混排资源，即便这里只需要分类路径。

两次聚焦 profile：全菜单 1.067/0.959 s；两次路径投影 0.692/0.615 s，245 次 content、约 251 次目录连接。`node_choice_rows` 名为快照，但其构建仍是逐父级查询；菜单项懒展开没有消除这段预先工作。其余还有控件/QSS 构建与 ActionPolicy 的图像帧判定。该证据独立于 Hover、缩略图、任务恢复，**不把全量路径读取误归为 G-14 已修过的同一函数**。

### 3.2 新卡片暂缓与业务输入是不同责任

- EmojiCard 的按下/移动/释放（emoji_card.py:568/574/616）不以 `_is_loaded` 或 Hover 完成为条件；业务资源身份来自当前绑定，发送路径仍验证实际文件。
- `VirtualGallery._drain`（virtual_gallery.py:251）确实在左树导航选择定时器/动画活动期间暂停准备新卡片。它不是显式禁止旧卡片业务操作，但新位置可能还没有可命中的控件。不能以缩短预览延迟修这个等待。
- 导入结束重建侧栏后，记录到 pending=40、busy=True 的 drain，多次让出而不绑定；结束回调后约 0.24 s 才绑定首个新条目。它是“投影已更新→控件出现”的独立阶段。
- GUI 同步计算时，已经到达的操作也会等待事件循环。独立线程每 100 ms 投递的 probe 在干净导入结束跨界时最长等 1.116 s；这是事件循环入场延迟，不是 OS 输入/Photon 测量，也不能与同一回调的嵌套耗时相加。

## 4. 导入可靠提交 → 图库可见

主要链：ImportQueue → ImportThread/ResourceImporter → Index.register（T-06 同事务凭据）→ **files_finished** → `_queued_files_finished` → EntryModel.sync → VirtualGallery → GalleryThumbnails。

### 4.1 自动更新是否等整批结束？

当前 `_progress` 仅更新请求/通知计数；没有每次接纳后通知图库投影。`files_finished` 在 `_finished` 发出；另一个合法边界是 `_show_batch` 进入重复项决策时，先展示已完成的普通项。因此准确结论是：**不是所有场景绝对只在整批结束，但普通导入没有逐提交的渐进呈现；通常等批次结束，或重复决策边界。**

本轮无手动排序的干净实验：32 个既有资源的测试分类，8 张真实大 GIF，原 T-09 判定后自动选择 keep 作为测试驱动，8 项完成、kept=8、failed=0。等待人工决策时间未计入，未改生产决策实现。总经过 16.80 s，不代表普通无重复导入吞吐。

| 首项时间分解 | 可靠提交后的累计时间 |
| --- | --- |
| Index.register 返回（资源/关系/凭据已提交） | 0 |
| 等待剩余 7 项接纳，进入 files_finished | 5162.8 ms |
| 结束回调 `_queued_files_finished` 返回 | 再 1106.5 ms |
| 新条目首次绑定 | 6506.9 ms |
| 首次占位绘制（loaded=False） | 6535.4 ms |
| 缩略图附着 | 6553.1 ms |
| 首次带缩略图绘制（loaded=True） | 6572.4 ms |

八项提交至占位绘制分别约 **6535、5602、5059、4325、3596、2848、2125、1392 ms**。绑定至附着约 46–186 ms。卡片可以先绘制占位再显示图像；延迟主体在更早的通知与 GUI 更新，不是必须等缩略图才能绑定。这里的绘制完成是 Qt paintEvent 证据，仍非 DWM 实际呈现时刻。

集中重复接纳阶段没有逐项 `_progress` 回调；不能伪造每项进度时间。普通检测阶段的进度与最终完成更新均已记录。来源读取/规范化由原 worker 执行，干净轮 `_save_file_source` 的检测/接纳调用约 222–757 ms，规范化约 169–689 ms；Index.register（含 T-06 凭据）约 7–186 ms。计时不能再拆成独立磁盘复制/解码 CPU 时间而不增加探针。

### 4.2 结束刷新和排序

初轮无 cProfile 的结束更新约 1.614 s；聚焦 profile 约 2.764 s；清除已知实验残留后低开销轮约 1.106 s。系统负载、缓存与 profile 开销均不同，不把这些数字当优化前后。

聚焦链：`_queued_files_finished → sidebar.refresh_list` 约 2.476 s，其中 `_as_node_id` 在已经拿到稳定 ID 时仍先走旧 category_labels 路径；完整建树/图标渲染及兼容投影重复执行。118 个自定义图标经 `render_node_icon → QPixmap(path).scaled()` 在 GUI 读原图；该轮节点图标约 0.574 s。随后图库增量更新约 0.287 s，EntryModel.sync 对已缓存节点仍可逐节点查询；干净轮增量更新约 0.063 s。

通过实际 `_reorder_by_drop`/稳定 DropTarget 的导入并发路径，9 次调用约 **169–591 ms**，无并发顺序校验异常；排序会带入新提交条目，部分可见延迟降到约 0.3–1.3 s，但末项仍等待收尾。未重演真实外部投放，也未对每次最终顺序增加断言，不能将本调查等同 G-25 全部人工验收。早期直接读顺序再写的探针发生竞态，被修正为原业务拖放入口，其失败样本不计为产品缺陷。

T-06 没有引入“所有缩略图解码完成才提交”的门槛，也没有改变主要投影通知边界；检查点与资源一起提交，新增记录仍来自同一队列。没有做相同负载开关检查点的 A/B，**不能据本轮数据给 T-06 指定开销比例或撤销可靠性**。

干净轮首次去重索引墙钟仍约 6.85 s，发生在 worker、锁前；4175 个登记资源的持久特征 size/mtime 均有效，原快照另有一个未登记且 Pillow 不可解码的文件。没有足够 CPU/I/O 分解证明这里发生全库重复解码；这仍是待细分的后台等待，不能直接叫 GUI 阻塞。

当前 GalleryThumbnails 使用两条解码线程、视口/缓冲区请求优先；变更视口会撤去未开始的 wanted 请求，已运行任务不强停，完成后校验卡片身份。不存在可据本轮证明的无限线程积压；也不能把 CacheNone 说成零解码或零文件读取。非零帧耗时与后续任务竞争仍需保留观察，不默认加线程、静态化动画或 CacheAll。

开发探索轮三轮隐藏/显示及最小化/还原：无 refresh_content、无新 decode，但约 306 次 bind 调用。多数是几何/状态同步而非资源身份重建；不能把次数直接算重新解码。原预览会取消/停止；show_gallery(refresh=False) 不主动全量刷新，默认 refresh=True 的其它入口仍可刷新，未穷举全部托盘手势。ClipboardService 的激活可用性检查走现有广告/序号路径，没有读取剪贴板原文/抓图测试，未证明它是本轮热点。
