# NekoriEmojy｜发布后下一版本更新规划与分级评估

> **规划版次**：v0.1 · 2026-10-21  
> **规划对象**：已公开发布版本之后的下一轮更新；**不预先锁定版本号或发布时间**。  
> **性质**：需求归档、优先级和实施顺序建议；不是 Codex 立即修改代码的授权。  
> **依据**：用户本轮完整需求、其对浏览器采集接口的补充限定，以及前期 Suzu 继承度、窗口底层与公开仓库源码调查。静态源码核对不等于已完成运行时复现。

## 0. 结论摘要

本轮不是一次单纯的 UI 细节更新。实际主要矛盾集中在五处：

1. **窗口宿主长期回归**：圆角、窗口边缘缩放、窗口拖动延迟，应合并做一次有边界的底层整理，而不是继续在显示事件后叠加补丁。
2. **图库交互契约没有完全闭合**：分类树、内容节点、顶部标签栏、拖拽反馈及位置判定已有共享基础，但多个入口的实际行为不一致。
3. **任务进度和通知身份不一致**：迁移过程存在显示 100% 后仍继续执行的阶段；进度和完成通知可能分裂成多条记录。
4. **大数据量路径和故障恢复尚未形成完整体验**：图库反向滚动、分类卡顿、批量导入与 OCR 中断恢复需要分别处理性能与可靠性。
5. **新功能应尽量复用已有能力**：自动检查更新、重复启动唤醒、剪贴板导入快捷键可以在现有服务上扩展；采集浏览器扩展**仅预留 Nekori 接口与预分类契约**，本轮不开发插件。

**建议策略**：先修影响核心操作、数据可信度和反复回归的问题；再做交互完整性与设置打磨；将持久任务恢复作为独立的较高成本工作块推进。无需因此创建企业级任务平台、重写图库或迁移完整窗口框架。

## 1. 分级约定

| 等级 | 定义 | 纳入版本的规则 |
|---|---|---|
| **P0 — 重点修复** | 已报告的高频故障、影响核心操作、严重性能问题、用户无法确认操作是否完成，或存在多次修复后回归 | 优先排查并在下一次稳定更新中争取闭环；若缺少复现，应标记待复现，不能仅凭猜测改动 |
| **P1 — 下一轮功能与体验** | 明确的日常效率需求、体验完整性、已有组件的行为一致性 | 建议纳入本轮迭代，但可按依赖分批交付 |
| **P2 — 可后置细节** | 低风险、可独立完成的视觉/便利性改动，或当前不影响主要流程 | 有余量时合并，不拖累 P0/P1 |
| **R — 研究或接口预留** | 实际方案、接口边界尚需验证；本轮不承诺完整功能 | 只做最小调研、明确数据契约或必要的内部接入点 |

**难度口径**：低＝局部控件或接线；中＝多组件协同；高＝涉及 Windows 原生窗口、任务持久化或跨模块状态。难度是相对规模，不是工期估算。所有优先级均可在运行复现后微调。

## 2. 完整需求清单与验收标准

### A. 窗口与桌面集成（W）

| ID | 需求／现象 | 等级 | 难度 | 实施边界与最低验收 |
|---|---|---|---|---|
| **W-01** | **圆角多次修复仍回归；透明材质与圆角边界不一致** | **P0** | 高 | 核查 `window_shell.py`、`materials.py`、`main_window.py` 的轮廓所有权；明确 Qt 自绘、窗口裁剪、DWM、Acrylic 各自责任。主窗/设置/工具窗在显示、缩放、恢复及主题变化后外轮廓持续正确。不要简单再追加一次 `apply_rounded_corners()`。 |
| **W-02** | **鼠标拖动窗口边缘调整宽高再次失效** | **P0** | 中高 | 与 W-01 同批检查非客户区命中、边缘/四角 resize hit-test、窗口区域与 DPI 坐标。四角及四边均可抓取，边缘宽度合理；既不能拖不动，也不能大面积误判为缩放。 |
| **W-03** | **窗口拖动有明显延迟／缓动** | **P0** | 中高 | 对照 [Issue #7](https://github.com/Nekori347/NekoriEmojy/issues/7)；区分系统拖动链、窗口透明合成、鼠标事件与 UI 阻塞。不预设是特定系统版本的缺陷。鼠标拖窗应跟手，没有额外动画滞后；不破坏标题栏按钮及缩放。 |
| **W-04** | **程序已运行时，双击 EXE 要唤起现有主界面** | **P1** | 中 | 保留单实例；第二个实例向已有进程发送“显示主窗口”请求，不再静默退出。不重复初始化资料库、不新建第二主程序、不改变用户当前数据。安装版与 ZIP 运行版入口均核对。 |
| **W-05** | **检查更新与启动检查更新** | **P1** | 低中 | 保留手动检查入口；新增启动后的异步检查（建议具备设置开关和适度限频）。网络超时不阻塞主界面；无更新不重复通知；有更新沿用现有更新中心与既有完整性检查。不得自动安装未确认更新。 |
| **W-06** | **复制表情后按一个全局快捷键直接导入 Nekori** | **P1** | 中 | 显式触发读取当前剪贴板图片、图片文件/路径或可识别的图片 URL，复用导入/去重及任务反馈。快捷键可设、避免与发送表情快捷键冲突；不监听剪贴板后未经触发自动导入。目标分类依据当前交互上下文或明确规则，不猜测。 |

**窗口专题结论**：W-01/02/03 是一个底层调查与修复工作包，但三种现象并不必然同根。保留 PySide6 与现有 `NekoriWindow`；先验证当前宿主链，再决定是否收敛原生处理。无需为了“脱离 Suzu”而重写全部 `MainWindow`。

### B. 图库、分类、节点与标签（G）

| ID | 需求／现象 | 等级 | 难度 | 实施边界与最低验收 |
|---|---|---|---|---|
| **G-01** | “全部表情”页面的大小调节、历史使用控件被移到左侧 | **P1** | 低 | 核对该页既定设计及过去正确位置，再恢复布局；避免把用户原本的布局回归误当成新设计。窗口缩窄后也不能挤压主要操作。 |
| **G-02** | “回顶部”按钮与最底部节点展开控件重合 | **P1** | 低 | 基于实际可见节点/浮动控件矩形做避让；尺寸、滚动和节点展开变化后都不覆盖可点击目标。 |
| **G-03** | GIF 作为分类图标时，未使用用户指定的缩略图帧 | **P1** | 中 | 检查分类图标数据、解码及缓存键；确保和资源缩略帧选择使用同一个有效帧语义。更换帧后立即刷新，重启后不退回首帧。 |
| **G-04** | 拖到节点时展开的选择菜单没有跟随鼠标 | **P0** | 中 | 复核拖放会话内菜单坐标来源、跨控件和滚动时的刷新；菜单贴近当前鼠标/目标且不跳位，不挡住实际落点。 |
| **G-05** | 将分类拖到顶部标签栏没有正确生效 | **P0** | 中 | 查明当前预期语义（打开标签、定位节点或重排）后核对 Tab 接收与 `DropTarget`；拖放反馈与最终动作一致，不吞掉操作或误移动节点。 |
| **G-06** | 两个节点中间无法判定插入独立表情 | **P0** | 中 | 在节点与资源混排布局中区分 `INSERT_BEFORE/AFTER` 和 `INTO`；能把资源精确插到两个节点之间，而不是误归属节点内部。保存后顺序稳定。 |
| **G-07** | 节点折叠条没有显示已设置的分类图标 | **P1** | 低 | 折叠/展开条从同一节点图标数据源读取；图标变化时同步，缺失文件有明确回退。 |
| **G-08** | 左侧分类树右键新建节点出现在顶部而非底部 | **P1** | 低 | 在目标父分类下默认追加至末尾；根节点、子节点均正确，不改变其他手动排序。 |
| **G-09** | 分类树图标与图库节点图标应可独立调整大小 | **P1** | 中 | 分离两个视图的尺寸设置，分别预览和持久化；调整一处不意外改变另一处。 |
| **G-10** | 调图标大小时图像变化不明显，判定 Box/占位明显变大 | **P0** | 中 | 同时检查图像实际绘制尺寸、布局占用与命中区域；保留必要间距，但不能只放大空白框。不同尺寸下能直观看到图标变化。与 G-09 一起修。 |
| **G-11** | 标签页区域滚轮应滚动标签列表，而不是切换当前标签 | **P1** | 低 | 滚轮改变可视标签位置、保持当前已选节点不变；触控板与普通滚轮方向合理。 |
| **G-12** | 标签较多时左右翻页按钮方向相反 | **P0** | 低 | 左键显示更靠左标签，右键显示更靠右标签；在两端正确禁用或停止。 |
| **G-13** | 标签页展开时明显左右晃动 | **P1** | 中 | 检查标签尺寸计算、激活线动画、滚动位置及布局反复重排。展开、选择、窗口缩放时无可见左右抖动。 |
| **G-14** | 表情很多时列表滚到底后向上滚明显卡顿 | **P0** | 中高 | 对真实大图库采样：虚拟卡片复用、缩略图队列、反向滚动时的同步工作与缓存失效；优先去除主线程热点，不重新发明整套虚拟图库。 |
| **G-15** | 分类数量较多时明显卡顿 | **P0** | 中高 | 与 G-14 分开定位：分类树刷新、节点渲染、选择/展开和模型重建；大分类库切换与展开平顺，不能靠停止刷新掩盖错误。 |

**图形交互专题**：G-04/05/06 共用拖放逻辑；G-03/07/09/10 共用图标呈现链；G-11/12/13 共用标签行布局。按小组件成组修复，比按 UI 截图逐点补丁更能防止回归。核查现有 `drop_contract.py`，**先用已有的 `INTO / INSERT_BEFORE / INSERT_AFTER / APPEND` 契约**，不另造拖放状态系统。

### C. 迁移、进度、通知、恢复与诊断（T）

| ID | 需求／现象 | 等级 | 难度 | 实施边界与最低验收 |
|---|---|---|---|---|
| **T-01** | Suzu 迁移时提醒不要关闭软件 | **P1** | 低 | 在迁移确认及进行中明确提示“请保持源数据可用、不要关闭参与迁移的程序”；根据实际迁移方式区分正在运行的 Suzu 实例与磁盘数据目录，不制造不准确的强制前提。 |
| **T-02** | Suzu 大批量导入进度显示 100% 后长时间无响应 | **P0** | 中 | 进度划分为资源复制、分类创建、成员关系、排序整理、刷新完成等实际阶段；真正全部提交后才显示完成。最后阶段至少持续显示阶段名称/忙碌状态/已耗时，失败可查看原因，不出现虚假完成。 |
| **T-03** | 通知与进度是两条独立消息，同一操作各发一条 | **P1** | 中 | 以稳定任务 ID 表示一次业务操作，从等待/运行更新为完成/失败/中止；同一任务原位变更状态。非任务提示仍可独立出现，但不能把单次导入的结束事件新增为第二条完成通知。 |
| **T-04** | 进度条的停止按钮改为红色高亮 | **P2** | 低 | 使用统一的危险操作视觉色，悬停/按下明确；保持停止与真正取消/可恢复动作的语义区分。 |
| **T-05** | 通知栏折叠图标左新增红色垃圾桶：清除所有完成通知并折叠 | **P1** | 低 | 只清理完成状态的可清理通知并收起面板；不误删进行中、等待恢复或尚需处理的错误任务；不删除业务数据。 |
| **T-06** | 导入、OCR 识别遇关闭软件、掉线、关机等异常后自动发现中断任务并确认恢复 | **P1（大项，可拆批）** | 高 | 对真正可续做的工作保存最小任务检查点；再次启动识别未完成任务、展示完成数和来源状态、由用户确认恢复。已完成工作不重复导入/识别；缺失来源进入等待状态。不要承诺进程任意指令级断点恢复。 |
| **T-07** | Log 诊断、Log 留存上限机制 | **P1** | 中 | 统一日志目录与关键任务关联 ID，错误可供诊断；按大小/数量或天数轮转并设硬上限，避免无限写盘；提供简便查看/导出；不把隐私图片内容或敏感信息无必要写入日志。 |

**迁移已知静态线索**：`services/suzu_migration.py` 当前有一段可见进度在资源与分类完成后达到总数，随后还要写分类成员关系、重排资源并刷新图库。即便这些后续步骤最终成功，也会让用户看到“100% 却还没有完成”。应先修真实性，再考虑展示动画。

**通知已知静态线索**：`fluent_ui/components/feedback.py` 已有 `upsert_task()` 和具名任务，同时还存在 `legacy` 和独立通知路径。应收敛已有任务标识，不另建大一统后台任务平台。

**故障恢复边界**：

- **文件导入**：记录请求来源、已完成项、失败/等待项；继续未处理项，利用去重避免重复。
- **OCR**：以资源稳定 ID 对应待识别任务；结果完成后再标记完成，失效资源可跳过或待确认。
- **Suzu 迁移**：只读源端、目标端采用可重复执行或可核对的阶段，避免重建重复节点/成员关系。迁移恢复成本较高，先核查现有幂等能力，再决定纳入 T-06 首批还是后续子批。
- **硬盘断开**：明确“等待源设备连接”，不自动死循环重试，也不把源缺失当成任务已完成。
- **真正崩溃/强制结束**：仅恢复最后可靠提交的任务单元；不能假装能恢复尚在内存中的任意操作状态。

### D. 外部采集接入：严格限定为接口预留（E）

| ID | 需求 | 等级 | 难度 | 本轮实际交付 |
|---|---|---|---|---|
| **E-01** | 为未来浏览器采集插件接入 Nekori 预留接口，允许**在插件层先分类、再导入**；未来同一插件也可适配 Eagle | **R / P2** | 低中（仅契约） | 核对现有 `resource_import.py`、`library_index.py` 能否表达外部图片/文件 URL、目标分类稳定 ID 或路径、标签、来源、请求标识与导入结果。编写最小、可扩展的接收数据契约；有明确必要时补一个内部批量导入入口。**不要求本轮建立公网/本机 HTTP 服务，不开发浏览器扩展、油猴脚本、广告拦截规则引擎，也不开发 Eagle 适配器。** |

采集层将来可以借鉴广告拦截器的**站点规则匹配和资源发现方式**，但那是外部插件自己的实现问题，不属于本次桌面更新。Nekori 只需要能接收“资源 + 已选择的分类/标签”并复用去重/入库功能。与 Eagle 的兼容由插件适配层实现，而不是让 Nekori 直接依赖 Eagle 内部协议。

建议数据契约关注：`request_id`、资源集合（文件或 URL）、目标分类稳定 ID／可解析路径、标签、来源 URL、是否允许创建缺失分类、成功/跳过/失败结果。具体字段名称与传输方式暂不固化。**接口预留不等于现在必须启动本地服务。**

## 3. 建议工作包及依赖关系

| 工作包 | 包含需求 | 为什么归为一组 | 前置条件 |
|---|---|---|---|
| **WP-A 窗口宿主稳定性** | W-01、W-02、W-03 | 圆角、拖窗及边缘缩放共享底层窗口与原生消息机制，已经多次回归 | 基于已发布版先复现，保存具体 Windows/显示设置/缩放条件；可在隔离窗口样例验证候选方案 |
| **WP-B 图库拖放闭环** | G-04、G-05、G-06、G-08 | 统一落点、拖放效果和最终资源/节点顺序 | 先核对已有统一 DropTarget 与实际 UI 入口 |
| **WP-C 图标及分类呈现** | G-03、G-07、G-09、G-10 | 同一图标在分类树、图库节点、折叠条与缩略帧之间的映射 | 明确两个视图尺寸的独立设置与缓存失效规则 |
| **WP-D 标签栏与浮层** | G-01、G-02、G-11、G-12、G-13 | 位置、滚轮、翻页、抖动与避让问题 | 结合真实 UI 截图/交互确认期望，不重构全站导航 |
| **WP-E 大数据量流畅度** | G-14、G-15 | 共同体现主线程工作过重，但图库与分类树热点不同 | 分别采样大表情库/大分类库；只修证据指向的热点 |
| **WP-F 任务反馈和迁移** | T-01、T-02、T-03、T-04、T-05 | 迁移进度真实性、通知身份和操作反馈互相关联 | 先统一可见任务状态，再做通知栏细节 |
| **WP-G 长任务持久化** | T-06、T-07 | 恢复要依赖可记录、可辨认的任务单元与错误信息 | WP-F 的任务身份先稳定；先确认已有导入/OCR 可续做边界 |
| **WP-H 日常效率** | W-04、W-05、W-06 | 均可复用现有单实例、更新和导入服务，彼此耦合低 | 可与其它工作包并行，不能阻塞主界面或破坏单实例 |
| **WP-I 采集接口准备** | E-01 | 为未来外部插件留出接收+预分类能力，不开发插件本身 | 以现有入库能力为基线，仅定义最小契约 |

**实施顺序建议**：

1. **基线与复现**：仅对 P0 记录环境、复现动作和可观察故障；保留已发布安装包作为对照，不进行大规模预先审计。
2. **先做 WP-A**：一次性理清窗口形状、材质、命中与拖动的职责，避免其它 UI 更新再次触发旧补丁。

## 6. 重点设计原则与禁止的误区

1. **不以消除 Suzu 源码痕迹为目标**。`MainWindow` 历史沿用并不代表在 Suzu 窗口外又套完整窗口；需要删除的是重复职责及失效补丁，而不是历史来源。
2. **窗口轮廓要有唯一最终责任层**。Qt 视觉圆角、窗口区域与 DWM/透明材质不能在没有明确切换规则的情况下同时决定窗口真实外形。避免把窗口圆角问题简单缩减为“Windows 10/11 分别补一段”。
3. **一次用户操作对应一个任务身份**。进度、完成、失败、继续属于同一任务状态的转换，不应另外创建一个结果通知。已有 `upsert_task()` 等基础，应以收敛接线为主。
4. **保留数据安全约束**。Suzu 只读迁移、不接管或清理原目录；异常后恢复以幂等可核对为前提；不通过自动静默重试掩盖错误。
5. **只修已确认的卡顿热点**。图库与分类树虽表面类似，但其开销来源可能不同；先用轻量证据定位，避免重写虚拟化或一口气加入多层缓存。
6. **复用现有拖放协议**。分类树、混合图库与标签栏落点语义统一，但各容器拥有自己的几何计算；不能靠创建更多状态判定绕开错误命中。
7. **浏览器采集只预留接口**。预分类发生在未来插件侧；Nekori 的职责是接收并导入，不做网站解析/过滤、不内置 Eagle 插件架构。
8. **避免过度设计与重复验证**。不为单次更新构建新平台式框架、无价值的哈希/兼容测试层或大规模截图测试；以最小充分代码检查、真实交互和针对性回归为准。

## 8. 建议交给 Codex 的执行原则

- **第一步**只做发布版本与当前工作树的差异确认、需求映射和 P0 的最小复现，记录未能复现的事实；别先连续重构。
- **一个工作包一次实施**，每完成一包就进行相关手动验收，保持回退点。与其它工作包有共享文件时避免交叉覆盖。
- **不为视觉细节牺牲稳定性**；窗口材质可有明确的降级策略，但不能出现矩形漏底、边缘不可缩放或明显输入延迟。
- **不要自行更改数据格式/清理用户数据**；任何迁移持久化变动，先确认兼容与恢复边界。
- **不要自行决定发布版本号、推送或发行**；实现计划与实际代码提交、发行审批分离。
- **不把采集接口预留扩展成浏览器插件研发项目**；如接口现在没有消费者，可以先留简短契约，不为了“未来可能”引入常驻服务或复杂配置。
