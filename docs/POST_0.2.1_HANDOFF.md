### 2.2 Sol 接管时的唯一一次现状盘点

在**用户原有的 Codex GPT-6.1 Sol 对话**中，优先用本地事实完成：

1. 读取已有 `AI_START`、`CURRENT`、相关 `DECISIONS`、本计划与 #8 / #9 / #7；必要时读取本地 `DevData` 中 WP-A 的原型和调查记录（以实际目录为准，可能包含 `post-021` / `wpa` 命名），不要假定某文件必然存在。
2. 读取 `git status --short`、当前分支与 HEAD、已发布 Tag、相对 `main` 的差异，以及**工作区中哪些代码/文档/原型已经变更、哪些尚未提交**；不执行任何破坏性 Git 命令。
3. 为 W-01/02/03 分别标记：`已调查 / 有原型 / 已修改源码 / 已机器验证 / 已人工验收 / 待处理`，附最短证据与路径，不能以“跑了原型”代替“修复了产品”。
4. 先提出**一个**真正可交付的下一个小修复任务，优先沿用 Astra 已落地且可以验证的成果；若两个问题确认共因才合并。不重新搜索大量社区材料、重做全仓审计或比较整套窗口框架。
5. 检查文档与分支是否已妥善隔离；只有确定可安全继续时才修改产品源码。必要时整理一段短的 WP-A 交接记录至项目现有合理位置，不创建新的大型审计体系。

## 4. Sol 适用的实际开发顺序（非强制版本承诺）

**切片 0｜接手并继续 Astra WP-A**：确认窗口原型、改动与调试记录 → 选择一个可证实的 W-01/02/03 子问题 → 实施修复 → 真实窗口短场景验证 → 暂停人工验收。**只先启动这一切片**。
