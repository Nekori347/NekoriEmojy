### 1.4 F02：现有数据结构和生命周期

**[F｜源码]** 开发环境以项目根目录为 `base_dir`；打包环境以 `sys.executable` 所在目录为 `base_dir`。数据目录为 `base_dir/data`，图片为 `data/images`，所以原发布版实际使用 `bin/data/` 存放用户运行数据。

| 原文件 | 表 / 结构 | 已确认字段或作用 |
|---|---|---|
| `features.db` | `image_features` | `image_path` 主键；`md5`、`dhash`、`phash`、`quality_score`、`created_at` |
| `metadata.db` | `image_metadata` | `image_path` 主键；`tags`、`keywords`、`created_at` |
| `categories.db` | `categories` | `id`、唯一 `name`、`icon_path`、`sort_order` |
| `categories.db` | `category_images` | `category_name` + `image_path` 复合主键 |
| `order.db` | `item_orders` | `image_path` 主键、`sort_order` |
| `recent.db` | `recent_history` | `id`、唯一 `image_path`、`updated_at` |
| `config.json` | JSON | 用户设置；旧迁移器明确不迁移它 |
| `categories.json` / `order.json` | 旧分类对象 / 顺序数组 | 又被部分代码称为“双写备份”，实际行为见下文 |

图片引用通常经 `os.path.basename` 归一为文件名。图片、分类和排序逻辑上已经分开存储，问题是部署位置没有隔离，不能描述为“它们全在同一个文件里”。

原启动顺序为：检查 JSON 迁移 → 执行需要的 JSON 到 SQLite 迁移 → 同步全库去重 → 创建 `StorageService` → 建表、读取哈希、孤儿资源修复 → 死链清理和 UI 初始化。

**DB / JSON 不是可靠的独立双备份：**

1. `get_all_images()` 优先 `order.db`，没有排序记录时才回退 `order.json`。
2. `get_all_categories()` 只要从 DB 取得至少一个分类，即使关系为空，也不继续读 JSON。
3. `needs_migration()` 只根据任一旧 JSON 是否存在判断；迁移向已有 DB 执行 `INSERT OR IGNORE`，对应步骤成功提交后删除 JSON。
4. 资源包导入后调用 `force_reload()`，从 DB 重载并重写 `order.json`、`categories.json`、`metadata.json`、`category_icons.json`、`hashes.json`。

因此不能说“JSON 永远被忽略”，也不能把它当作完整、独立、永久可回退的备份。不同新旧状态混合时，DB 优先、冲突忽略、JSON 删除和回写会影响恢复结果。

### 1.5 F03：排序、自愈与覆盖更新风险

**[F｜源码]** `get_all_images()` 枚举支持的图片，默认文件名倒序；DB 有排序时返回 `new_filenames + valid_saved_filenames`，即未记录图片在已有排序图片之前。`_repair_orphaned_resources()` 为缺失索引的文件读取字节、补 MD5；发生修复后调用 `get_all_images()` 和 `save_order()`。后者删除 `item_orders` 全表并按当前列表重建，同时写 JSON。

分类列表由 `categories.sort_order` 排序。`category_images` 没有独立的分类内顺序字段；`get_images_by_category()` 用全局排序过滤成员。因此保留原版语义时，分类内展示顺序依赖全局排序，不应擅自新增一套独立排序体系。

**[F｜源码及成品包]** `build_nuitka.py` 会把构建目录中存在的整个 `data/` 复制进发布目录。实际检查的官方 v1.11.6 ZIP 内有 `bin/data/`、用户数据同名 DB、配置、缓存和 28 张默认 PNG。只读查询结果为：

| 内容 | 当时发布包中的数量 |
|---|---:|
| 分类 `Suzu` | 1 |
| `category_images` | 28 |
| `item_orders` | 28 |
| `image_features` | 28 |
| `image_metadata` | 28 |
| 最近使用记录 | 0 |

**[F｜结构性结论]** 在解压时实际选择替换同名文件的覆盖更新操作下，可以形成“旧图片因没有同名替换文件而留存，分类和排序 DB 被发布包 DB 替换”的状态。随后未被 DB 记录的旧图可能被当作新图处理，自愈又可能持久化新生成的顺序。程序与用户数据的更新边界缺失，足以解释核心现象。

**[F｜用户报告]** 用户多次覆盖更新后分类和排序失效，数千张图片仍在。**[H]** 没有事故前后 DB、文件复制日志和当次启动日志，尚不能证明每次事故具体覆盖了哪些文件、经过哪些自愈分支。

### 1.6 F04：资源交换包的事实与能力边界

**[F｜上一阶段 JSON 检查]**

| 清单字段 | 值 |
|---|---|
| `format_version` | `1` |
| `package_id` | `4e0de227-fa78-40a7-8bcb-02acd1a958ca` |
| `exporter` / `app_version` | `pc` / `unknown` |
| `exported_at` | `1788354831167`；UTC 2026-09-02 13:13:51.167，UTC+8 21:13:51.167 |
| `resources` / `assets` | `1502` / `1502` |
| `categories` / `relations` | `8` / `7` |
| `total_asset_bytes` | `1,840,329,819` |
| `skipped` | `33` |
| 目录记录格式 | GIF 944，PNG 558 |

8 个分类为：赛马娘、GBC、车万、邦邦、Other、MRFZ、管人、术力口。只有 7 个资源的 `category_refs` 非空，1495 个为空；7 条关系分布为赛马娘 5、GBC 1、Other 1，其余 5 个分类没有资源关系。

7 个有关联的 `display_name` 均以 `20260902` 开头。源码文件名格式是 `YYYYMMDDHHMMSSffffff`，只能据此提出“可能为导出当天新增或重新分类”的假设，不能确定关系丢失时间。

33 个跳过项扩展名均记录为 `.gif`，其 reason 中的头部十六进制呈现 `RIFF....WEBP`。这强烈提示 WebP 容器使用了 `.gif` 名称，**没有打开实体文件复核**，也不知道错后缀的形成原因。

**[F｜导出源码]**

- 输出 `manifest.json`、`catalog.json`、`assets/`，读取图片、分类、metadata 和 features。
- 资源目录包含哈希、资产路径、尺寸、格式、创建时间、显示名、关键词、质量分和 `category_refs`。
- 不读取 `order.db`；没有手工全局顺序字段；最终按 `(created_at, display_name, sync_key)` 排序。
- 按魔数接受静态 PNG / GIF，APNG、WebP 等跳过；`_read_app_version()` 硬编码返回 `unknown`。
- `_load_categories_readonly()` 优先 DB；只要取得分类名称就返回，即使关系稀少。DB 不存在、异常或没有任何分类时才可能读 JSON。

**[F｜导入源码]**

- 校验版本、清单计数、大小、SHA-256、MD5、sync key；现有 PNG 以像素 MD5、GIF 以文件 MD5 查重。
- 重复图不复制，但仍按包内引用补分类关系并计为 skipped；该分支不补 `item_orders`。
- 新图保存后写特征、metadata、关系，并按包遍历顺序追加到排序尾部。
- 不预建全部分类声明，只有处理到分类引用才建立相应分类。在干净目标中，这份包按该代码路径预计只建立 3 个被引用分类，而非全部 8 个。

**结论限定：** 该格式无法表达和恢复手工排序。用户报告“只建立几个分类，约 98% 仍未分类”与包内容及源码一致；完整 `assets/` 未提供，未重跑该 ZIP 的实际往返。关系可能在覆盖更新、迁移、历史操作、读源选择或导出匹配等不同阶段减少，故障层未定。

### 1.7 F05：重启后首次粘贴慢的已知机制

**[F｜用户报告]** 每次重启或开机后的第一次复制粘贴导入慢，同一运行周期后续导入快；尚无正式计时结果。

**[F｜源码]**

1. `StorageService._sync_key_index` 初始化为 `None`。
2. `_standardize_and_save()` 的文件 MD5 快路径未命中后，相关分支计算像素哈希并请求 `_get_sync_key_index()`。
3. 首次索引同步遍历 `data/images` 的支持文件并计算 sync key；静态 PNG 可能用 PIL 解码为 RGBA 计算像素 MD5，GIF 读取全文件计算 MD5。
4. 索引仅存在进程内，重启失效；后续导入复用它。
5. `handle_global_paste()` 的 `file` 路径走后台线程，`image` 路径直接在 UI 当前调用 `storage.save_image(data)`，有阻塞 UI 的机制。
6. 启动去重是另一套路径，没有给此索引赋值。`find_duplicate_groups()` 的有效特征两两比较为 O(n²)；1502 项若全部有效，对应 1,127,251 对，实际数量取决于有效项目。

**[H]** 此机制与现象高度吻合，但扫描、解码、启动去重、磁盘缓存、防病毒和剪贴板类型各占多少耗时仍需测量。不能把启动索引视为已经预热首次粘贴，也不能未经计时认定只有一个耗时来源。

### 1.8 F06：Resize Cursor 的后续准确现象

**[F｜后续用户报告，取代早期较窄描述]**

- 鼠标到左 / 右缩放边缘出现横向 `↔`，明显移回内部后仍可能残留。
- 鼠标到上 / 下边缘出现纵向缩放光标，移回内部后也可能残留。
- 早期“顶栏实际能拖动窗口，却显示横向缩放箭头”保留为一个相关表现。

产品问题应按“**离开窗口缩放区域后，光标没有及时恢复当前位置应有状态**”处理，不能只修标题栏。横向、纵向残留是现象描述；内部哪一层刷新失败仍是推测。

**[F｜旧源码调查]** `MainWindow` 继承 `qframelesswindow.FramelessWindow`，使用 `StandardTitleBar`。项目源码未发现显式给标题栏设置横向 / 纵向 resize cursor 的代码。横向 `QSplitter` 手柄宽 4 px，内容区有 32 px 顶部边距，不能仅凭它存在就认定标题栏命中该手柄。

圆角处理使用 `DwmSetWindowAttribute` 和 `SetWindowPos(...SWP_FRAMECHANGED)`，显示 / 唤醒后在 0、100、500、1000 ms 重试圆角和 flags。外部无边框库的历史讨论涉及 DPI、多显示器和负坐标；检查过的某版边缘常量约 5 px，但未识别发布包精确依赖版本。

**[H]** `WM_NCHITTEST` 与 Qt 系统移动判断不一致、坐标 / DPI 转换、flags 重新应用、依赖组合或 cursor 状态刷新都可能有关。不能认定“边缘判定带过大”“QSplitter 导致”或某个上游 issue 就是根因。

## 2. 项目目标与不变原则

### 2.1 R-BASE：定位、名称与既有能力

**[R]** 制作基于 SuzuEmojy 的个人自用修改版 **NekoriEmojy**，尽量复用上游代码、整体 UI 风格和正常业务逻辑，不从零重写。程序显示名称统一使用 NekoriEmojy；保留 GPL-3.0、原作者版权、上游来源和必要修改说明。

**未明确要求修改或删除的原功能默认保留。** 包括但不限于：开机自启、分类及其编辑 / 删除 / 图标、普通 Tag、右键操作、Ctrl+V、多选、筛选、搜索、窗口拖动与缩放、资源交换包导入导出、最近记录、去重等正常能力。列举不代表允许删除未列出的功能。

改名、移动入口、数据迁移或更换内部实现都不能成为功能消失的理由。开机自启须在 ZIP 成品上实际验证；不能因调整名称、程序位置或取消传统安装流程而遗失。托盘图标没有明确要求修改，默认保留其行为。

### 2.2 成功目标

**[R]** 整体使用方式类似更轻量的 Eagle：程序负责 UI、搜索、浏览、导入、OCR 和管理；用户自己选择的独立资源库负责资源、数据库和整理状态。程序可以 ZIP 覆盖更新、删除旧版本或重新下载，重新连接同一资源库后恢复原有使用状态。导入只复制资源，不移动或破坏原文件。

用户已有数千张图片能够安全迁移，实际可读取的分类、关系、顺序、metadata 和设置得到保留。日常导入、拖放分类、布局设置更易用，首次粘贴和 cursor 问题得到有证据的修复。本地 OCR 为现有搜索提供文字召回，并允许人工修正且永不被自动任务静默覆盖。日志默认低开销，出现问题时可主动导出诊断包。

**范围修正：** 后续明确要求已取代备份文档中的“必须交付传统 Windows 安装程序”。本期以 ZIP 解压即用为主，不要求传统安装器；“由用户选择独立资源库，数据库和重要数据跟随资源库”也已确定，不再把核心数据位置列为 `%LOCALAPPDATA%` 与便携目录二选一。仍未确定的是内部布局、定位机制和具体迁移实现，见第 10 节。

### 2.3 维护约束

**[R / 执行约束]**

- 先明确数据归属和调用链，再改界面和功能；修复根因，不为页面、文件路径或入口堆特判。
- 同一业务操作有统一核心逻辑；多个 UI 入口调用同一服务，避免重复验证、去重、写库和错误反馈。
- 每类持久数据有明确权威来源，不继续扩大 DB / JSON 相互竞争、相互覆盖的关系。
- 用户不可重建内容与可重建缓存分开；缓存重建不得改写人工分类、排序或 OCR 修正。
- 只做需求相关和必要的底层整理，不整体换框架、不做架构洁癖式重写，也不把新职责继续塞进巨型类。

- 性能改善不能通过删除既有功能实现，也不能把首次导入的等待原样搬到启动、搜索或浏览过程。

## 3. 数据所有权与架构边界

### 3.1 数据所有权表

以下是落实 **R-DATA、R-LIB、R-MIG、R-OCR** 的逻辑边界。资源库根目录由用户选择；数据库、资源和整理状态必须在这个自包含单位内。示例内部名称不构成固定表结构或路径。

| 数据类别 | 归属 / 权威性 | 更新、清理和备份规则 |
|---|---|---|
| EXE、DLL、Qt / Python runtime、静态程序资源、默认应用图标 | 程序发布层，可随版本替换 | 可以更新；不得把构建者的运行数据一起带入 |
| 程序默认配置、默认素材、内置 OCR 模型（若最终采用） | 程序资源 / 种子资源，须与运行数据区分 | 默认值可发布；用户修改后的偏好和已导入素材不能只存在程序目录；模型分发方式待评估 |
| 用户图片、GIF、WebP、其他支持资源、分类、关系、分类顺序、手工全局排序 | 资源库内用户资产 | 跨升级保留，整库复制 / 迁移和回滚覆盖；不能按缓存处理 |
| 普通 Tag、用户编辑 metadata、分类图标、收藏 / 状态等已有或未来资源元数据 | 资源库内用户资产，由数据库统一管理关系与状态 | 不能因为特征重建或模型升级而丢失；存储范围列举不自动要求新增“收藏”等未提出的 UI 功能 |
| OCR 人工修正、手填隐性文字、人工清空的意图 | 资源库内用户资产 | 与机器结果分层，自动任务和清缓存不可覆盖，进入用户数据备份范围 |
| 用户设置、布局偏好、个性化图标选择、资源相关配置 | 资源库内可迁移偏好 | 重新连接库可恢复；设置导出管理偏好，不能借此导出整库 |
| 最近使用记录及其他原有持久状态 | 资源库内，按原产品语义保留 | 不因本次架构整理擅自降格为可随意丢弃的数据 |
| 数据库、资源索引、文件 / 像素哈希、特征、必要缩略图、搜索规范化结果 | 资源库内索引和派生数据 | 跟随整库迁移；普通程序更新不能清空或无条件重建，有失效证据时才受控处理 |
| 机器 OCR 候选、OCR 队列 / 索引状态 | 资源库内派生结果与任务状态 | 持久保留并随库迁移，避免因更新、改路径或重启而重扫；人工部分独立保护 |
| 最近资源库位置、机器关联等引导信息 | 可恢复的连接信息 | 具体保存方式待定；即使丢失，手动选择库仍可恢复全部库数据，不能成为唯一业务数据副本 |
| 日志与诊断缓存 | 有界诊断数据，具体位置待定 | 自动轮换、按需导出；不能使库连接依赖旧程序目录，也不能只为诊断扫描图片 |

“可重建”只描述数据来源和受控维护能力，不授权升级时重建。普通 ZIP 更新、删除 / 重下程序、重连或搬迁库，都要保留数据库和有效索引，不以全库重新导入、OCR 或哈希计算替代读取已有状态。必要结构变化走 R-SCHEMA，缓存失效和人工主动重建也不得影响用户资产。

资源库内部可以类似 `assets/`、数据库文件、`thumbnails/`、`cache/` 和库描述文件，但名称和布局待实现选择。库描述文件若存在，只承担清楚的库身份 / 版本职责，不能另造与数据库竞争的分类、排序或 OCR 权威副本。

### 3.2 单一权威来源和写入职责

**[R / 执行约束]** 分类、排序、Tag、OCR、资源索引及元数据通过资源库内数据库统一管理。单一权威来源针对同一份业务状态；物理上一份数据库还是按现有结构组织多个数据库文件，可通过 D03 验证，不能机械理解为必须大重写。无论文件数量多少，它们都必须跟随同一个资源库，由同一数据访问边界协调一致性。

旧 JSON 兼容应集中在迁移 / 兼容边界，不能让正常运行长期在多个来源之间猜测、双向合并和覆盖。具体 schema 版本、迁移登记、旧 JSON 保留策略为 D03；选择后写清楚入口与冲突规则。

资源库生命周期和统一位置解析职责提供当前库上下文，存储、图片导入、搜索、设置、OCR 和资源交换使用同一约定，避免各模块自行拼路径。核心数据不再写入程序旁的 `data/`，也不拆散到用户需要分别配置的技术路径。

库内资源引用应能跨库根目录改变保持有效，优先评估库内相对引用和现有稳定身份；不能依赖旧电脑盘符、原下载路径或旧 EXE 目录。最近打开库的定位信息可以另有轻量机制（D02），但它丢失时必须能重新选择已有库，不能丢失业务数据。

缓存修复、哈希补建或 OCR 重建应仅更新自己负责的数据。若旧 `save_order()` / 自愈调用链涉及人工顺序，必须拆清副作用并用回归验证，不以“修索引”为名重新生成用户排序。

### 3.3 建议职责边界

**[执行约束 / D：具体模块组织可按现有代码选择]** 不机械照搬以下名字；先复用可用职责，只有需要时才抽取接口。

| 职责 | 负责 | 不应负责 |

| 资源库生命周期 | 创建 / 打开 / 切换 / 重新连接 / 迁移库，提供当前库上下文，管理任务归属和可写状态 | 每个模块独自猜测活动库、静默创建空库掩盖旧库不可用 |
| Import Service / Pipeline | 输入归一、格式验证、去重、标准化、保存、feature / metadata 更新、结果通知、OCR 入队 | 为每个按钮复制完整实现 |

| Settings Service | 配置结构、默认值、保存、校验、导入 / 导出、恢复默认 | 图库完整备份、各控件分别写配置文件 |
| Diagnostics | 统一日志、阶段计时、异常、状态摘要和导出 | 每个 Bug 新建独立日志系统 |

### 3.4 统一业务链路

**[R / 执行约束]**

1. Ctrl+V 与“粘贴导入”先走同一个剪贴板处理入口。
2. 剪贴板、本地单 / 多文件、浏览器拖放通过输入适配获取图片，再汇入同一导入核心；文件来源默认复制进当前资源库，不移动、删除、重命名或改写源文件，不默认纯外部路径引用。
3. 导入核心统一完成格式验证 → 去重 → 标准化与保存 → 元数据 / 特征提交 → 结果通知 → OCR 增量入队。
4. 单张拖分类、多选拖分类、右键“添加到分类”汇入同一关系变更核心。
5. 搜索入口仍只有现有搜索栏；OCR 与普通 Tag 在数据语义上隔离，在查询结果上统一。

新图只有在库内保存成功后才视为可搜索资源并进入后续任务。并发保存、重复图、失败重试时不能制造悬空关系、重复记录或旧 OCR 覆盖新内容。切换资源库时，已发出的导入 / OCR / 搜索任务必须仍归属于原库或被安全停止，不能因全局路径变化把结果写到另一个库。这是落实一致性需求的验证约束，具体事务 / 队列实现不预设。

资源交换包是已有专用格式与批量语义：需要时复用底层存储能力，但不强行用日常图片导入的默认行为覆盖它的清单校验、分类映射和排序语义。本阶段不以“统一 pipeline”为理由大改 exchange 格式。

### 3.5 图片导入、设置、资源交换与整库操作必须分清

| 概念 | 目标 | 本期范围 |
|---|---|---|
| 日常图片添加 | 把当前图片加入图库 | Ctrl+V、按钮、本地拖入、浏览器拖入；高频入口 |
| 设置导入 / 导出 | 转移软件偏好 | 本期明确要求；不包含数 GB 图库 |
| 原资源交换包 | 交换现有格式能表达的资源和关系 | 保留功能，入口移到设置；不宣称能还原手工排序 |
| 整个资源库复制 / 搬迁 / 重连 | 保持全部资源和整理状态 | 本期明确要求自包含库和迁移能力；不能让用户重新逐图导入 |
| 迁移 / 数据库升级回滚备份 | 在改造中保护真实用户数据 | 本期必须有可验证的保护与恢复路径；人工 OCR 属于用户资产 |
| 面向用户的完整灾难备份产品 | 完整库的长期备份 / 恢复 | 独立功能，格式与产品范围未定，不能借本次整理默认新增 |

因此“完整灾难备份格式待定”不等于可以跳过整库可复制性、迁移前保护或恢复验证，也不允许把人工 OCR 归入可清理缓存。自包含库可以在一致状态下整体复制和备份；是否另加专门备份容器、历史版本 UI 等产品功能仍待定。

### 3.6 R-DEPS：成熟方案优先，依赖数量和复杂度受控

**[R]** 新功能和重构不要求从零实现。遇到通用问题，先检查当前语言 / 框架的标准能力、项目已有依赖、官方推荐方案、可靠成熟库和有长期维护记录的开源实现，再决定复用、借鉴或自行实现。可靠方案已存在时，不为快速交差重写复杂基础设施；也不为“用了现成方案”无条件增加依赖。

本原则覆盖数据库与迁移、ZIP / 压缩包、OCR、复制 / 拖放 / 剪贴板、缩略图与缓存、日志、配置、路径与资源库、备份恢复、完整性校验和 Windows 原生窗口行为等。自动更新若未来进入范围，也适用；**这条选型原则不把自动更新变成本期功能**。

**引入任何新的第三方库、项目或代码前，至少检查并记录：**

| 检查项 | 所需结论 |
|---|---|
| 技术兼容 | Python、Qt / PySide、Nuitka、目标 Windows 环境能否正常使用 |
| 维护状态 | 近期更新 / 社区活动与长期维护记录；记录检查日期，不只凭项目名称判断 |
| 实际验证基础 | 用户量、真实应用案例或长期使用记录是否足以支撑可靠性判断 |
| 已知问题 | 是否存在明显未解决的稳定性、安全性或性能问题，是否影响当前用例 |
| 依赖负担 | 依赖树、ZIP 与解压后体积、启动时间、内存 / CPU 的实际影响 |
| 外部条件 | 是否要求额外 runtime、后台服务、联网服务、语言包或特殊硬件 |
| 许可证 | 是否与当前项目使用、修改及分发要求兼容；引用 / 复用须保留必要声明 |
| 耦合和替换 | 能否通过清晰接口接入，未来升级 / 替换是否会牵动大量业务代码 |
| Windows 可靠性 | 在目标系统和真实打包成品中的行为，不以其他平台或开发环境替代 |
| 更简单的替代 | 标准库、现有依赖、成熟小模块或较少代码的方案是否更合适 |

选择优先级为：**可靠性与数据安全 > 与现有项目兼容 > 长期维护性 > 简单程度 > 性能与体积 > 开发速度**。

不能为了少写代码牺牲维护性，也不能为“零依赖”重复制造成熟项目已解决的问题。若现成项目只解决部分需求，可使用公开 API、引入库、参考架构，或在许可允许时复用有限代码；不必整体搬入项目。必须记录来源、精确版本 / 提交、许可证、用途、引入原因和后续维护边界。

禁止把来源不明的代码片段、博客、论坛答案或未验证仓库中的关键实现直接复制进项目。外部讨论可以作为线索，关键实现依据应回到官方文档、代码和可复现测试。数据迁移、更新、备份恢复等高风险功能优先长期验证的实现方式，不用临时脚本或实验性方案充当正式核心实现；隔离实验脚本可用于验证，但不能替代可靠的产品实现。

遇到引入依赖与自行实现都有明显取舍的决定，在实施计划中先列候选、优缺点、推荐方案、理由，以及对体积、性能、维护和兼容性的影响。可逆原型和低风险细节可自行推进；明显改变用户数据语义或造成难以回退的绑定时，带具体结果再确认，不先做不可逆决定，也不为每个小依赖暂停开发。

本文件不代选库，也不宣称已检查任何候选的当前维护状态。实施时应按当时官方资料和实际构建验证，并维护一份简洁的依赖 / 方案决策记录。

## 4. 按依赖拆分的实施阶段

### 4.1 阶段安排

**[执行约束]** 先使资源库生命周期和数据写入可控、问题可观测，再统一导入和关系操作；布局功能依赖这些基础，OCR 正式接入依赖评估和数据契约。ZIP 与资源库边界应早期验证，最终发行包在功能冻结后完成。

| 阶段 | 前置条件 | 主要工作 | 本阶段退出条件 |
|---|---|---|---|
| **P0 基线冻结** | 取得源码，使用隔离目录 | 检出固定提交；建立 NekoriEmojy 工作仓库 / 分支并保留历史或来源；记录实际依赖；验证空数据启动和原版构建；记录既有功能；为通用基础能力建立成熟方案调查与决策清单 | 原版可运行、可构建；原功能结果和环境可追溯；新依赖有 R-DEPS 检查入口，不先盲目扩展依赖树 |

### 4.2 防止重复实现的阶段规则

- 不先为粘贴、本地拖放、浏览器拖放各写一套，再用后续“重构阶段”收拾重复逻辑。
- 分类网格和纵向视图共享成员关系与排序；视图变化只改变呈现和命中方式。
- 设置先明确默认值、预览态与持久态，再绑定网格和布局开关，避免多个控件各写配置。
- P1 做最小可用日志和导出，后续模块接同一系统；不用等 P6 才拥有问题证据。
- P1 可按“库身份与位置解析 → 版本迁移 / 旧源导入 → 切换和搬迁一致性 → 删除程序后重连验证”拆成可检查的小步；库边界未成立前不接入正式 OCR 写入。
- ZIP 最终成品可以最后打包，但资源库独立性、程序目录可删除和覆盖更新安全不能留到最后验证。传统安装器已退出本期必做范围。
- 每阶段记录变更理由、验证结果、剩余问题和回滚方法。已通过的相关检查只在新改动或失败需要时重跑。
- 技术未决项只约束依赖它的工作。可逆工程选择由 Codex 测量并记录；会改变需求范围、用户数据语义或明显超出偏好时，再带具体结果确认，避免将全部开发变成逐项询问。

## 5. 具体功能需求

本节标为 **[R]** 的内容是明确产品要求。标为 **[D]** 或“可选”的内容不能擅自升级为必做功能或已定实现。

### 5.1 R-DATA：更新时保留全部用户资产

**[R]** 程序与用户资源库彻底分离。程序目录不保存不可丢失的用户数据；ZIP 更新只更新程序内容。图片、GIF、WebP 和其他支持资源、分类、分类顺序、图片关系、手工全局排序、普通 Tag、OCR 隐性搜索数据及人工结果、收藏 / 状态等资源元数据、资源索引、数据库、必要缩略图、用户设置和资源相关配置，统一属于资源库。

要求从发布与运行边界解决问题，不能只给 `categories.db`、`order.db` 写若干“覆盖时跳过”的特例。正式 ZIP 不得带入用户数据库、用户图片、私人配置和开发缓存。程序自身可携带默认配置和静态资源，但用户修改后的唯一偏好不能留在可删除的程序目录。

普通更新不能覆盖、清空、重新初始化或无条件重建资源库 DB、分类、关系、排序、Tag、OCR、索引或用户整理数据。未来新增数据同样遵守资源库归属，不能再散回程序目录。需要结构升级时按 R-SCHEMA 迁移，不能把新建空库当作升级。

**验收指向：T02、T03、T05。**

#### R-LIB：独立可自定义资源库

**[R]** 首次运行让用户选择已有资源库或创建独立资源库。用户只管理一个“资源库位置”，不分别配置 DB、图片、缩略图或 metadata 路径。

设置中应能查看当前库位置、更换当前库、迁移库、重新指定已有库。实际库根目录由用户选择，例如 `D:\MyEmojiLibrary\`；具体内部名称可调整，资源、DB、索引和整理状态必须组成可独立复制、迁移、备份和带到另一台电脑的数据单位。

必须区分三种动作：

- **切换 / 重新连接：** 打开已存在的库，不复制、重建或重新导入全部资源，不改变其整理结果。
- **迁移：** 将同一个库完整迁到另一目录 / 磁盘并继续使用，保留图片、分类、关系、排序、Tag、机器 / 人工 OCR、DB、索引和其他元数据。
- **从旧 SuzuEmojy 导入迁移：** 读取旧格式并转换到新库，遵守 R-MIG；不是在原旧数据目录上直接试验。

**[执行约束]**

- 库应位于程序可删除 / 覆盖的目录树之外。选址时验证实际路径关系，不能只凭两个路径字符串看起来不同就认定独立。
- 缺失、断开的盘符、无权限或不兼容的库应给出清晰状态和重新选择入口，不能静默创建空库覆盖已整理状态。
- 迁移前处理当前写入，完整复制并校验一致性，目标成功后再切换。失败保留可用源，记录日志；不在验证前删除源库。
- 迁移后引用不依赖原库绝对路径，也不依赖导入前源图片位置；中文、空格、同名文件和换盘符要验证。
- 复制 / 迁移整库后，已有有效 OCR 和资源索引继续可用，不以重新全库计算冒充恢复。
- 切换库时隔离尚未结束的导入、OCR 和搜索结果，避免写错库或显示前一库的结果。

**[D01 / D02]** 库内目录结构、库识别描述和“最近资源库”定位机制待实现验证；不是核心数据放在哪里未定。可记住上次库实现自动连接；若定位信息丢失，重新选择同一库仍必须恢复全部库状态。

**验收指向：T06、T25、T26、T27。**

#### R-SCHEMA：数据库版本升级

**[R]** 数据库跟随库保存版本状态，程序检测版本并按正常迁移机制转换结构、保留数据。禁止通过删库、新建空库、清数据或要求重新导入来完成升级。

迁移失败要有错误日志，尽可能保持原数据库和可回滚状态，允许重新尝试。自动检测 / 迁移不意味着可以无备份原地破坏唯一数据库。具体迁移引擎、事务与备份方式、版本登记以及中断恢复方案按 R-DEPS 和 D03 选择。

**[执行约束]** 对较新或不兼容 schema，旧程序不能误当空库初始化。回退应使用兼容程序或经过验证的升级前备份；不能未经验证承诺任意旧 EXE 都能直接读新结构。

**验收指向：T04、T23。**

### 5.2 R-MIG：从 SuzuEmojy 安全迁移

**[R]** 用户已有数千张图片，不接受把“重新手工整理”当作迁移方案。迁移尽力保留实际能读取到的数据，不猜测已经丢失的历史分类或顺序。

迁移流程至少满足：

1. 将旧 SuzuEmojy 数据视为只读来源；识别实际目录和实例，不能根据目录名字猜测正确源。
2. 先保护可用原始数据，形成可核验、可回滚的备份 / 副本，再在隔离目标执行迁移。
3. 检查图片、categories、category relations、order、metadata、settings，以及应保留的分类图标等原有状态。
4. 同时存在 DB / JSON 时先报告各自统计、关联和冲突。不能简单把“DB 非空”或“JSON 存在”当作完整正确的证明。
5. 迁移真实可读取的数据到 NekoriEmojy，记录源到目标的资源对应关系，保证分类和顺序引用能对应到图片。
6. 完成后给出数量和失败原因；核对图片数、分类数、分类关系数、排序记录数、metadata 数、跳过数、失败数及配置处理结果。
7. 中断、异常或失败不能破坏原库；重新尝试应可判断已有进度，不能悄悄重复导入或覆盖更多内容。

**[执行约束]** 备份必须能还原一致的数据状态。具体使用停写后的文件副本、SQLite 一致性备份或其他方法待实现验证；不能仅因“复制过目录”就宣告有可用备份，也不能在源程序继续写入时将不一致快照当成功。

**[D03 / D17]** DB / JSON 冲突的具体合并策略、一次性或长期兼容范围须结合真实样本决定。首次安全迁移已经确定，不能因长期兼容未定就省略它。发现冲突时保留证据和原文件，不沿用“导入成功即删除唯一旧 JSON”的破坏性流程。

可恢复性参考（沿用调查结论，不是已经完成恢复）：

| 能取得的旧数据 | 理论可恢复内容 | 边界 |
|---|---|---|
| 更新前完整 `bin/data` | 图片、分类、关系、顺序、metadata 等，信息最完整 | 在隔离副本验证，不能再用带运行数据的发布包覆盖 |
| 旧 `categories.db` + `order.db` | 对得上图片的分类关系和全局顺序 | 最好同时保留其他旧 DB 和图标 / 配置 |
| 旧 `categories.json` + `order.json` | 可能迁移分类和顺序 | 避免污染 DB；原 JSON 另留副本，不能直接运行会删除它的旧迁移器 |
| 早期资源交换 ZIP | 包内实际记录的关系和资源 | 无手工顺序字段，不等于完整恢复 |
| 本次清单对应 ZIP | 目录中记录的 7 条关系及可用资源 | 不能恢复未写入包的分类或旧手工顺序 |

若需要寻找恢复线索，可检查旧解压目录、系统历史版本、文件历史记录、同步盘版本历史和旧磁盘备份。此处保留调查路径，不宣称这些位置现在一定有数据。

**验收指向：T02、T04、T05。**

### 5.3 R-ZIP：解压即用、覆盖更新与删除程序后恢复

**[R]** 以 ZIP 便携程序作为主要发行方式，不要求传统安装。ZIP 仅包含主程序、运行依赖、UI 资源、程序默认配置及其他必要程序组件。整体名称为 NekoriEmojy，用户补充中的 SuzuEmojy 目录示例不改变已确定的新名称。

- 标准更新流程：下载新版 ZIP → 解压覆盖程序内容 → 启动 → 自动连接原库 → 保持全部整理结果。
- 自动定位失败时，至少允许重新选择已有库并完整恢复。
- 用户可以删除整个旧程序目录，再下载到原位置或新位置；只要库仍在，重新连接后恢复原状态。
- 程序目录删除与资源库删除是独立行为；任何清理程序功能都不能顺带清库。若未来提供清库，必须是明确选择。
- 保留开机自启并验证便携运行、程序位置变化后的使用路径；不能因无安装器而删除该能力。
- 当前不要求自动检查更新、网络更新服务或在线下载安装；传统安装器退出本期必交付范围。

**[执行约束]** 可删除程序本体是数据架构要求，不是授权在用户唯一程序 / 图库上执行删除实验。使用隔离程序副本与测试库证明。覆盖时程序是否需关闭、依赖残留如何处理，应形成简单真实的 ZIP 更新说明，不退回要求用户手动保护几个 DB 文件的方案。

**验收指向：T01、T03、T06、T24。**

### 5.4 R-IMPORT：日常图片添加和统一入口

**[R]** 保留 Ctrl+V，新增可点击的 **“粘贴导入”** 按钮；两者使用同一剪贴板入口。与本地 / 浏览器拖放共享后续图片导入逻辑，包括格式检测、去重、标准化、保存、feature / metadata 更新、UI 结果、错误反馈和 OCR 入队。

**所有入口默认复制进入当前资源库，管理库内副本。** 复制文件后粘贴、资源管理器拖入、浏览器复制图片后粘贴及原有其他入口均适用。不得移动、删除、重命名、改写用户原文件或改变其位置；默认不采用只保存原外部路径的引用模式。

例如源为 `D:\Downloads\123.gif`，导入后源仍在，库内另有受管理副本。之后移动 / 改名 / 清理源文件，库内表情仍可浏览、搜索和使用。无文件来源的剪贴板图像则保存为新的库内资源。

库内可以按统一规则命名、查重和处理格式，但不能改变源文件；不能静默把动态 GIF / WebP 的动画丢掉或损害资源。基于真实格式验证支持范围，不能仅凭扩展名认定容器。WebP 纳入资源库资产与导入验证；现有交换包只支持 PNG / GIF 不代表图库本身只能管理这两种格式。

**[D]** 外部纯引用模式若未来需要，独立设计，不作为本期默认或必做能力。任何新导入入口都必须通过同一“源不变、库副本独立”的契约测试。

**本地拖入：** 支持文件资源管理器、桌面及其他提供文件拖放的软件，支持单文件和多文件。对不支持格式给明确反馈，不能默默无反应；失败项不得让已成功项目和统计失真。

**浏览器图片拖入：** 目标是“网页图片 → 拖到 NekoriEmojy → 加入图库”，不要求先另存为。实际检查常见 Chromium 浏览器提供的临时文件、URL、MIME 图像、HTML 或其他载荷，按可用证据解析图片。

- URL 指向非图片时拒绝，网络或下载失败给出可理解的反馈。
- 获取、解码等耗时操作不阻塞 UI；获取成功后进入统一图片导入核心。
- 不能把浏览器拖图扩展成无关网页抓取器。
- 明确实际验证的浏览器与载荷类型，不能用一个 URL 示例声称已支持所有浏览器。

**[D10]** 浏览器兼容清单和具体载荷优先级待 Windows 实测。下载超时、资源限制、并发等参数按真实用例选择并记录，不在本文编造数值，也不为每个网页堆专用解析分支。

**验收指向：T07、T09、T10。**

### 5.5 R-PERF：首次导入性能

**[R]** 程序重启后，第一次导入不能因为已有数千张图片而再次同步扫描整个图库、让当前操作明显等待或长时间冻结 UI。

- 先测量已知调用链，再选择复用 / 持久化方案；优先复用现有 feature、file MD5、pixel MD5、sync key 等成果。
- 不维护没有必要的第二套同义身份或哈希索引。
- 必要的缺失索引补建尽量后台完成；当前图片导入不能等待整库扫描结束。
- 不把等待原样转移到启动，也不删除原有去重功能来换取表面加速。
- 日志能区分首次 / 后续耗时、是否扫描全库、主要阶段、线程和索引命中情况。

**[执行约束]** 哈希复用必须确认算法和内容语义相同。file MD5、pixel MD5、sync key 并非随意可互换的字段；索引失效、文件内容替换和并发导入时，仍须保持正确去重与保存结果。

**[D]** 尚未设定毫秒级验收阈值。以同机同样本前后比较和可观察的扫描 / UI 行为证明改善，再记录实际结果；不承诺没有测过的数字。

**验收指向：T07、T08、T09。**

### 5.6 R-CURSOR：修复离开边缘后的 Resize Cursor 残留

**[R]**

- 左右真实缩放边缘显示横向光标，上下边缘显示纵向光标，四角显示相应对角光标。
- 离开缩放区域后立即恢复当前位置应有光标；内部文本控件、链接和可交互区仍保持自身正常光标。
- 标题栏拖动、边缘缩放、最大化 / 恢复、多显示器和 DPI 行为继续正常。
- 问题覆盖整个状态转换过程，不能仅给标题栏强制设置 `ArrowCursor` 遮盖。

按需使用第 6 节的临时诊断记录 `WM_NCHITTEST`、全局 / 客户区坐标、窗口尺寸、DPI、屏幕、HT 值、cursor 变化及系统移动。依赖组合和根因确认前，不先假设必须换库、关闭无边框或移除原窗口能力。

**验收指向：T11。**

### 5.7 R-CAT：分类栏纵向 / 网格模式

**[R]** 保留现有纵向模式，新增“上图标、下分类名”的自适应网格 / 平铺模式。

- 设置中可切换模式、调整分类项目 / 图标大小、隐藏或显示名称。
- 左侧栏仍可拖拽改变宽度；列数根据实际宽度和项目大小计算，不写死。
- 宽度变化时实时重新排布；窄宽度下仍能正常使用。
- 保留原分类顺序、编辑、删除、图标等功能；切换视图不能改变成员关系或排序语义。

**验收指向：T12、T13、T15、T16。**

### 5.8 R-DROP：多选拖分类与目标高亮

**[R]** 多选后拖动任意已选项目，应把整个选中集合加入目标分类，不能只操作鼠标起始的一张。保留右键“添加到分类”和原有删除、导出、Tag 等多选能力。

单张、多张拖放及右键分类动作共享关系服务，成功后正确刷新图库与分类状态。这里的“拖到分类”按已有“添加到分类”语义实现，不擅自改为移除其他分类或移动图片物理文件。

有效目标分类必须明显高亮：

- 高亮跟随鼠标当前命中的有效目标。
- 离开目标、取消拖动或完成 Drop 后清除。
- 无效区域不能显示可投放的反馈。
- 纵向和网格模式都支持，宽度变化后命中仍正确。

**验收指向：T13、T14。**

### 5.9 R-SET：独立设置窗口、预览和配置管理

**[R]** 设置从主窗口内部二级跳转改为独立弹出的窗口。打开设置时主图库不被替换，保持当前图库状态，延续 Fluent UI 风格。

提供 **保存、恢复默认、导出设置、导入设置**。UI 偏好在调整时实时预览；“保存”负责持久化，不能等点击保存才第一次显示效果。

实时预览至少覆盖：分类纵向 / 网格模式、分类项目大小、是否显示分类名、多选位置、筛选位置、搜索栏位置，以及后续明确加入的 UI 偏好。

设置导入 / 导出处理软件偏好，可包含布局、图标尺寸、显示模式、功能开关、OCR 设置等，不是完整图库备份，不得悄悄包含数 GB 图片。恢复默认只作用于偏好，不应清除图库或人工 OCR 数据。

资源库设置只让用户管理一个库位置，提供查看、切换、迁移和重新连接入口。导入偏好或恢复默认不得悄悄改变当前库、把资源移走或清空库；若配置文件含原机器路径，按选择后的明确规则处理，不能无提示切换到错误目录。

**[执行约束]** 配置读取、保存、默认值和导入校验统一处理；错误文件不能覆盖已有可用设置。导入和预览后的保存语义需一致并有测试，不让不同控件自行持久化。

**[D11 / D12]** 设置窗口 modal / modeless 未定；未保存关闭时保留临时效果还是回滚、是否提供取消并恢复打开前状态，待交互选择。主图库保留当前状态不等于已经指定 modeless。选型后写清未保存关闭、恢复默认和导入设置的预览 / 持久化行为。

**验收指向：T15、T17。**

### 5.10 R-LAYOUT：入口位置与三个独立开关

**[R]**

1. 设置按钮移动到顶部窗口控制区域，靠近最小化、最大化、关闭，保持 Fluent UI 风格与窗口控件可用。
2. 原资源包导入 / 导出入口移到设置 / 数据管理区域，保留功能。高频图片添加和低频资源交换要有清楚名称与入口。
3. 设置提供 **多选、筛选、搜索栏** 三个独立布局开关，允许分别移动到左侧，不强制捆绑。
4. 适应侧栏宽度变化、分类网格和窄宽度，保证搜索框有可用宽度且不遮挡分类。

**验收指向：T15、T16、T18。**

### 5.11 R-ICON：运行时个性化图标

**[R]** 用户可以从当前图库选择一张图，作为 NekoriEmojy 的运行时图标，同步主界面左上角、窗口图标和 Windows 任务栏当前运行实例图标。

- 选择后立即生效，重启保持，可恢复默认。
- 不修改 EXE 内嵌图标。
- 原图被删除或不可用时自动安全回退，不影响启动。
- 选择 GIF 时允许使用稳定静态帧；不要求动画任务栏图标。
- 托盘图标没有明确变更需求，默认保留。

**[执行约束]** 任务栏当前运行实例图标须在 Windows 成品上验证，不能只在开发环境看到窗口图标改变就判定全部通过；也不把运行时需求扩大成改写固定快捷方式或 EXE 资源。

**验收指向：T19。**

### 5.12 R-EXCHANGE：保留旧资源交换能力并说明边界

**[R]** 现有资源交换包导入 / 导出先保留，主界面入口移入设置。暂不大改 exchange 模块或现有格式，不把它作为 NekoriEmojy 升级安全机制，也不宣传成完整灾难备份。

功能说明应与实有能力一致：可以交换支持的图片、部分 metadata 和包内记录的分类关系；现有格式没有手工顺序，部分格式会跳过。需要修正误导性“完整备份 / 全量还原”表述时，准确说明缺口，不夸大当前支持范围。

若后续新证据确认导出 / 导入缺陷，可按复现做有边界的修复并加相应验证，不因“只剩 7 条关系”直接选择重写。路径改造后须确认 exchange 读写同一个正确数据目录。

**[D13 / D14]** 真正完整灾难备份作为独立功能设计；是否以后让资源包携带 OCR 数据、是否扩展格式，均未确定。

**验收指向：T18、T23。**

### 5.13 R-OCR：本地隐性文字搜索

#### 5.13.1 产品目标和搜索入口

**[R]** 增加本地 OCR 表情文字搜索。图片写有“你怎么睡得着的”，即使没有人工 Tag，搜索“睡得着”也应能通过已保存的有效 OCR 文本找到它。OCR 服务于搜索召回，不是给普通 Tag 批量制造文字标签。

使用现有搜索栏统一检索原搜索信息、普通 Tag / keyword 和 OCR 有效文本，不新增独立 OCR 搜索框。用户不必选择靠哪一类字段查找；原搜索和筛选能力保留。

#### 5.13.2 数据语义与人工修正

**[R]** OCR 自动文本独立保存，不混入普通可见 Tag。提供清楚的 **“OCR / 隐性搜索文字”** 编辑入口，可结合详情、信息编辑、右键菜单或 Tag 附近的独立区域；具体位置待 UI 设计。

用户可以查看识别结果、删除错误字符、改错、补漏、清掉无意义结果，并在机器完全失败时手填搜索文字。保存后立即参与搜索，搜索优先采用人工修正后的有效内容。

逻辑上至少表达：

| 逻辑内容 | 作用 |
|---|---|
| 最近机器结果 | 作为候选和识别记录，可因重新识别变化 |
| 当前有效文本 | 实际用于搜索，可由机器初始结果或用户编辑形成 |
| 人工修改状态 | 保护人工版本，包括人工明确清空，不以“空字符串”等同未编辑 |

**[R]** 后台 OCR、首次补扫、批量重新识别、模型升级和索引重建不得静默覆盖人工结果。“重新 OCR”首先是生成新机器候选，不等于替换有效文本。

**[执行语义]** 用户主动清空无意义 OCR 后，应允许有效结果保持为空，不能因空值自动回退到旧机器文本；后台任务晚于人工保存返回，也不能覆盖刚保存的内容。具体字段与并发实现不预设。

**[D08 / D09]** 单张重新识别如何确认采用新候选、图片内容替换后如何展示旧人工内容，待具体交互决定。可选显示机器结果、有效结果、人工标记和重新识别按钮；必需的编辑 / 保存能力不能因这些展示细节未定被省略。

#### 5.13.3 语言范围与规范化

**[R]** 第一优先覆盖简体中文、繁体中文、英文、日文，并考虑中文 + 英文、中文 + 日文、假名 + 日文汉字、网络缩写和拟声词等混排，例如 `草 www`、`笨蛋 baka!`、`もうダメ了`。用户不应为每张图片手动选择语言。

第一阶段不新增图片语言分类功能，不加语言 Tag / 专用分类字段，不在 OCR 前额外跑语言检测模型，也不为了语言判定反复切换模型。目标是识别和搜索文字。

**[D：可采用的搜索派生处理]** OCR 异常空格、异常换行、英文大小写、全角半角、适当标点处理可以作用于搜索派生形式，不能破坏已保存的用户原文。

**[R]** 不强制繁转简，不把日文汉字改写成中文，不为“统一语言”改写原文。若未来让“后悔”召回“後悔”，使用搜索 alias / 映射思路；**第一版不强制简繁交叉召回**，见 D15。

#### 5.13.4 增量任务与状态

**[R]** 采用“图片进入图库 → 后台识别 → 结果持久化 → 搜索查询保存数据”的行为。

- 首次启用时后台处理既有图库，有进度且不阻塞正常浏览。
- 已处理且内容未变化的图片不重复识别；新增图只处理新增部分。
- 重启不全库重扫；无文字不是未处理，不能因为结果为空而无限重试。
- 日常搜索不执行 OCR；浏览、滚动不应触发重复识别。
- 至少区分未处理、已处理有文字、已处理无文字、识别失败。

**[D：可提供的维护能力]** 单张重新识别、批量重新识别、重建 OCR 索引的具体入口和组合可按第一版需要选择。只要实现任何一种，必须遵守人工保护、状态和后台性能规则；不能把它们当作删除人工信息的捷径。

#### 5.13.5 图片身份与内容变化

**[R]** 不仅凭文件名判断 OCR 是否有效。同名内容被替换后，旧机器 OCR 不能永久被当作新内容结果。

优先评估复用 file MD5、pixel MD5、sync key 和 feature 数据，避免重复身份体系。正确处理新增、删除、重命名、内容替换和重复图片。

**[执行约束]** 内容版本必须能让后台结果判断是否仍属于当前图片；过期识别任务不能写入新内容状态。人工文本在内容变化时采取安全策略，保留可恢复信息，不静默丢失或未经解释转移给另一张图。具体策略见 D07 / D09。

#### 5.13.6 GIF 与动态表情

**[R]** GIF 在已检查包中占多数，不能忽略动态图片。评估首帧、按时间抽帧、代表帧、变化检测及多帧文本合并去重，在召回和性能间取舍。**禁止默认对每个 GIF 全帧 OCR。**

抽帧策略、帧数 / 耗时边界和合并方法为 D06，需实测后确定。未来 APNG / 动态 WebP 可沿相似思路扩展，本期不无边界扩张格式范围，也不能因新 OCR 策略破坏原已有格式的正常浏览。

#### 5.13.7 备份、清理与准确率预期

**[R]** 机器结果原则上可重算，搜索缓存和队列可重建；人工修正与手填隐性文字是用户资产，进入用户数据备份 / 迁移保护范围。清缓存、重建 OCR、模型升级、软件升级不能丢失它们。资源交换包是否携带 OCR 仍未定。

OCR 是搜索辅助，不要求 100% 识别率。艺术字、描边、低清、彩色字、倾斜 / 旋转、背景干扰、小字、竖排、缩写和拟声词允许有错误；优先轻量、快速、有价值的初始结果和方便的人工修正。不能为极端准确率引入未经评估的超重环境。

后端和模型选择必须先完成第 7 节评估，再正式接入。

**验收指向：T20、T21、T22、T23。**

## 6. 轻量日志、诊断与导出

### 6.1 R-LOG：默认低开销

**[R]** 增加统一、轻量、有界的日志与诊断系统，正常运行时几乎感觉不到额外负担，出问题时能导出排查证据。先检查标准库和当前栈的成熟实现，遵守 R-DEPS；不为每个 Bug 临时另写一套日志。

普通模式记录有价值的生命周期、统计和异常，至少覆盖：

- 启动 / 退出、软件版本、构建版本、实际数据 / 资源库位置和连接结果。
- DB 初始化、schema 检测、迁移成功 / 失败、旧源迁移和资源库迁移结果。
- 图片导入成功 / 失败 / 跳过汇总及有用的分阶段耗时。
- 后台任务、OCR、拖放解析、网络图片获取、数据库和未捕获异常。
- 分类 / 排序异常，以及其他有诊断价值的 warning / error。

正常模式不持续记录鼠标每次移动、每个 UI paint、GIF 每帧或搜索每个字符。不能为产生“图片数”等日志扫描全库或重新解码图片。

**性能和可靠性要求：**

1. 不高频同步 flush，不把磁盘写入堆到 UI 关键路径。
2. 高频重复事件聚合、节流或仅记状态变化；日志轮换，设置大小 / 数量上限并自动清理旧日志。
3. 若使用异步队列 / 缓冲，也要有界，不能把“磁盘不增长”变成内存无限增长。
4. 日志写入失败、磁盘不可写或导出异常不能让主程序崩溃，也不能递归刷出更多日志。
5. 性能评估比较关闭 / 普通 / 诊断模式，验证浏览、导入、搜索、拖放和 OCR 并发下的影响。

**[D16]** 具体轮换上限、聚合窗口、队列容量和诊断持续方式按实测决定；不把示例数值写成用户指定指标。

### 6.2 临时诊断模式

**[R]** 可以提供临时更详细的诊断模式，用于 cursor 残留、首次粘贴慢、导入 / 浏览器拖放失败、OCR、迁移、分类和排序问题。详细模式不是默认永久开启状态。

| 诊断对象 | 按需采集的证据 | 约束 |
|---|---|---|
| Resize Cursor | 鼠标 / 窗口命中区域，全局 / 客户区坐标，窗口 / 客户区尺寸，HT 值，cursor 变化，DPI、屏幕、最大化 / 恢复，是否同时 system move | 仅在复现窗口内增加详细采样；必要短时完整命中事件使用有界方式，结束后关闭 |
| 导入性能 | 入口与剪贴板类型，图片数量，文件 / 像素哈希命中，是否触发整库扫描，扫描数 / 字节 / PNG / GIF 分布，解码 / 标准化 / 保存 / 通知耗时，UI 线程标识 | 不写剪贴板原始内容，不为统计另扫图库 |
| 资源库和迁移 | 当前库身份、源 / 目标类别、schema 版本、迁移步骤、计数与校验结果、异常阶段 | 保留足够定位信息，路径只留必要范围，不将所有数据库内容输出 |
| OCR | 当前库与任务归属、处理状态、候选版本、图片内容是否改变、排队 / 推理 / 保存耗时、人工保护是否生效 | 默认不写大量私人 OCR 原文，不逐 GIF 帧无条件刷日志 |
| 拖放 / 网络图片 | 载荷类型、选用适配路径、获取 / 校验结果和失败类别 | 不保存完整 HTML、Cookie、Token 或私有 URL 参数 |

旧调查提出“每次 `WM_NCHITTEST` 记录”是定位手段，不是普通模式的持续日志要求。应使用临时有界采样满足证据需要，避免诊断本身改变问题表现。

### 6.3 导出诊断信息

**[R]** 设置 / 数据诊断区域提供 **“导出诊断信息”**，用户可主动生成本地包交给后续 Chat / Codex 分析；导出不等于自动上传。

导出内容按可获得性包括：最近若干日志、NekoriEmojy / 构建版本、Windows 版本、Qt / PySide 和关键依赖版本、当前库连接状态、数据结构版本、图片 / 分类 / 关系等数量、OCR 状态统计、必要性能摘要、最近异常堆栈、相关设置摘要，以及不含图片实体的 DB 结构 / 状态摘要。

使用已有 DB / 索引状态提取必要统计；某项不可读取时说明未知 / 失败，不能为了凑齐摘要遍历解码数 GB 图片，也不能把未知数量填成零。

默认不包含整库、完整用户数据库、图片二进制、剪贴板完整内容、大量 OCR 私人文本、Cookie、密码、Token 或无关个人目录信息。确需路径、文件名或文本时只保留必要范围，导出时进一步控制可识别信息。日志位置和定位信息机制不得让图库恢复依赖旧程序目录。

诊断包生成失败要说明原因并保持主程序可用。记录格式、包格式和脱敏方法根据成熟方案选择，不增加不必要的远程服务或持续上传。

**验收指向：T28、T29、T30。**

## 7. OCR 技术评估与决策要求

### 7.1 R-EVAL：先评估，再正式接入

**[R]** OCR 后端、模型、运行时、GIF 策略和具体数据库表结构都不能因在讨论中出现过就被写死。遵守 R-DEPS，用真实表情样本和真实 Windows / Nuitka 成品验证后再决定。

候选名称可包括 Windows OCR、Windows AI TextRecognizer、ONNX Runtime、RapidOCR、PP-OCR / PaddleOCR、Tesseract 或其他轻量本地 OCR。**这些名称不是同层级的等价产品：API、运行时、封装和模型必须组成实际可运行方案后比较。** 本文不宣称任何一个已经满足中 / 繁 / 英 / 日混排、硬件条件或体积目标。

先按官方资料筛去不适配目标环境的方案，再对少量有竞争力的组合做隔离原型；不要求把每个名字都完整接入主应用。调查维护状态、兼容性和许可证时记录日期、版本与来源。

### 7.2 样本与识别指标

使用用户允许用于测试的真实表情或其他来源清楚的等价样本。已检查的旧资源包清单只能说明 GIF 比例和规模，不能代替尚未取得的图片测试集，更不能据此报告虚构识别率。

样本覆盖：

- 简中、繁中、英文、日文，及混排、假名 / 汉字、缩写、拟声词。
- 艺术字、描边、低清、小字、彩色字、旋转 / 倾斜、竖排和复杂背景。
- 静态图片、无文字图，以及文字仅在后续帧出现或跨帧变化的 GIF。
- 大图 / 大 GIF、损坏或无法解码文件，用于判断失败行为和资源边界。

为样本准备人工对照文字和代表性搜索词。以“目标搜索词能否召回图片”为重要指标，同时报告识别错误、需要人工修正的情况和失败率。结果按语言 / 混排 / 字体 / GIF 分层，不能只报一个平均准确率掩盖关键缺口。

### 7.3 性能、兼容性与成品体积

每个进入实测的候选组合至少记录：

| 维度 | 记录内容 |
|---|---|
| 组成 | 后端 API / 封装、runtime、检测 / 识别模型、版本、来源、许可证 |
| 效果 | 简中、繁中、英文、日文、混排及困难样本的召回和错误 |
| GIF | 首帧 / 时间 / 代表帧 / 变化抽帧比较，漏字、合并去重、耗时和内存 |
| CPU / 内存 | 模型加载与推理开销、峰值、后台处理时主 UI 的响应 |
| 速度 | 冷 / 热启动、单图和批处理时间、首次库索引速度与日常增量 |
| Windows | 实际系统版本、CPU / 硬件条件、是否要额外语言包、服务或特殊设备 |
| 发布体积 | 同一基线无 OCR 与有 OCR 的 ZIP 体积、解压后体积，以及模型 / runtime / DLL / Python 依赖分解 |
| 运行条件 | 是否离线可用、是否有额外安装 / 下载要求、无目标组件时如何失败 |
| 维护 | 依赖树、已知问题、API 稳定性、替换成本和长期维护依据 |

**必须用真实 Nuitka 发布构建测量体积，不只看模型文件或 Python wheel。** 在没有 Python 开发环境的目标 Windows 环境验证 ZIP 运行条件。若候选需要额外下载或系统组件，先如实披露其对“解压即用”和本地 OCR 的影响，不能悄悄加入联网服务作为必需路径。

### 7.4 体积与准确率取舍

**[R｜偏好，非硬阈值]** 旧需求以原软件约 76 MB 为体积参照，希望 OCR 增量理想约 **+20～40 MB**。这不是本次重新测量的基线，也不是绝对上限；应以 P0 实际成品建立比较口径。

尽量少模型，优先评估能用较少组件覆盖中 / 繁 / 英 / 日的方案，复用现有运行时，避免完整庞大 AI 环境，第一版不追求全球语言。合理方案略高于理想增量时，拆解模型、runtime、DLL 和依赖成本，再给出推荐与替代，而不是隐藏成本或直接砍掉语言需求。

准确率目标是有价值的初始搜索召回和可人工修正；不追求文档数字化级的完美文本，也不为了极端样本牺牲轻量与稳定。

### 7.5 OCR 评估交付与决策门槛

P4 至少输出可复核的候选对比、版本 / 来源、样本范围、识别与性能结果、真实包体差异、GIF 策略比较、推荐组合、未解决限制和选择理由。被筛掉的方案简要说明原因，不伪造未实际运行的数据。

进入 P5 前，至少明确后端与模型组合、目标 Windows 条件、GIF 有界处理策略及内容身份 / 人工保护接口。若候选没有同时满足关键语言、轻量和兼容目标，提交具体权衡结果；不得无声降低要求或把一个未经验证的库写进最终方案。

## 9. 禁止事项

### 9.1 证据和范围

- 禁止把“包内只有 7 条分类关系”改写成“导出器确定丢失分类”，或用模拟事故证明用户那一次事故时间线。
- 禁止把源码中的可能路径写成已复现根因；不能认定 cursor 必然来自 QSplitter、某个上游 issue 或过宽判定带。
- 禁止宣称未取得的完整 assets 已校验、用户真实 ZIP 已复验、OCR 候选已测或 Windows 行为已通过。
- 禁止把旧 Work 建议、早期问项和候选名称全部变成强制需求；新用户要求已解决的事项也不能继续列为开放选择。
- 禁止继续要求本期必须安装器发行，或把“自动更新”列在通用能力举例中解读成新增自动更新需求。
- 禁止删除未要求删除的原功能，或因为轻量 Eagle 的比喻复制整个 Eagle 的功能范围。

### 9.2 数据安全和资源库

- 禁止在程序目录保存唯一用户数据库、图片、人工 OCR、整理状态或唯一偏好；ZIP 不得携带运行库和私人数据。
- 禁止只靠“跳过几个同名 DB 文件”补丁解决升级边界；库不得放进可被整目录删除的程序树。
- 禁止把不可用 / 不兼容资源库静默当成空库创建，或要求用户重新导入全部资源代替迁移 / 重连。
- 禁止导入时移动、删除、重命名、改写源文件，默认禁止只记录外部路径的纯引用方案。
- 禁止普通升级、换程序位置、重连或搬迁库时清空 DB、分类、排序、Tag、OCR、有效资源索引或配置。
- 禁止将迁移失败解释为可直接删旧库重建；禁止在唯一真实库上做破坏性实验、先删源后校验目标，或静默删除旧 JSON / DB。
- 禁止把旧 DB 与 JSON 当作始终可靠的双备份，或把资源交换 ZIP 当作完整灾难恢复包。
- 禁止把哈希 / 缓存修复和人工分类 / 排序重写绑定；不能推断不存在于历史记录中的人为整理结果。
- 禁止资源库切换后将旧库任务结果写入新库，或让整库迁移后仍依赖旧绝对路径。

### 9.3 实现与依赖

- 禁止整体换框架重写、把所有新职责塞入巨型类，或为普通 UI 问题枚举页面 / 路径堆补丁。
- 禁止 UI 各自写数据库；Ctrl+V、按钮和拖放不能复制多套导入核心，单张 / 多张分类不能各写一套关系逻辑。
- 禁止已有可靠方案时为交差重写复杂基础设施，也不能为了“零依赖”重复造轮子。
- 禁止无条件增加依赖，或未检查兼容、维护、已知问题、许可和体积就引入关键库。
- 禁止复制来源不明或未经验证的关键实现；复用源码必须记录来源、版本 / 提交、许可证和原因。
- 禁止将临时实验脚本作为用户数据库迁移、备份恢复或更新的正式关键实现。
- 禁止在有重大取舍时先作不可逆绑定；普通低风险实现也不应被不必要的逐项确认拖住。

### 9.4 性能、OCR 和诊断

- 禁止重启后首次粘贴同步扫描全库，或把等待原样搬到启动；不以删除去重功能换速度。
- 禁止强制全局 `ArrowCursor` 遮盖根因，导致真实边缘、文本等区域光标错误。
- 禁止每次启动 OCR 全库、搜索时实时 OCR、随浏览反复 OCR、空结果无限重试或默认 GIF 全帧 OCR。
- 禁止 OCR 混入普通 Tag 失去来源；人工修改、手填和明确清空不得被后台任务 / 模型升级 / 重建静默覆盖。
- 禁止为了规范化改写用户原文、强制繁转简或把日文汉字转换成中文。
- 禁止未经评估写死 OCR 后端 / 模型，或只看模型 / wheel 大小而忽略真实 Nuitka 成品。
- 禁止日志默认记录高频鼠标、paint、GIF 帧、搜索字符，或无界占用磁盘 / 内存；日志失败不能拖垮主程序。
- 禁止默认导出完整图库、DB、剪贴板、私人 OCR 大段原文或凭据；不能自动把诊断包发送给他人。

## 10. 未决技术选择与待补证据

### 10.1 已确定事项，不再重复询问

以下已由当前请求和后续补充明确：

- 软件名 NekoriEmojy，基于 SuzuEmojy，保留未要求变更的原功能和许可 / 来源。
- ZIP 解压即用为主要发行方式，不要求传统安装器，不新增自动更新功能。
- 用户选择独立资源库根目录，资源库位于程序可覆盖 / 删除范围之外，数据库和重要用户数据跟随库。
- 用户只选择一个库位置；有创建 / 打开、位置查看、切换、迁移和重新指定入口。
- 导入默认复制到库内，不移动源，不默认纯外部引用；删程序后重连库恢复状态。
- 正常版本迁移保留数据，升级失败有日志和可回退路径；不是删库重建。
- OCR 是本地隐性文字搜索，四种主要语言及混排优先，人工修正受保护，与普通 Tag 隔离。
- 日志低开销且可导出；成熟方案优先但依赖受控。

后续补充中的“OCR 隐性 Tag / OCR Tag”在本文统一解释为已定义的 OCR 隐性搜索元数据，不改写为普通可见 Tag。未明确提出的新收藏功能、全球语言、多库自动合并和完整 Eagle 功能均不默认加入。
